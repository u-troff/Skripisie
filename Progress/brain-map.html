How it fits together

Two clients speak to main.py. Before the rover leaves, the dialogue code turns speech into a confirmed plan. After it leaves, mission.py runs the plan step by step. Both ask the same two models, through one provider layer, and mission.py moves a rover through one interface that has three implementations.

Reading order

Eleven stops, each with a question you should be able to answer before moving on. Line ranges come from the code, so they stay right if the files change and this page is rebuilt.

  1. Settings and logging

    Every module reads settings through one small loader. Knowing it first removes a lot of mystery from the rest.

    You should be able to answerWhere does a setting such as NAV_MODE come from, and what value does the code use when it is missing?

  2. The front door

    Two WebSockets carry the whole conversation. dialogue() handles everything before the rover moves. execution() starts the mission as a background task and feeds it frames.

    You should be able to answerWhich message starts a mission, and what must be true of the dialogue session for it to be accepted?

  3. The conversation

    A session walks CLARIFYING, PLANNING, VERIFYING and AWAITING_CONFIRMATION. Read the phase enum first, then the one function that runs the loop.

    You should be able to answerWhen does the loop stop asking questions, and what does session.capped record?

  4. Every model call

    Planner and VLM calls both end in provider.complete(). Read one caller from each side, then the factory they share.

    You should be able to answerWhat does a caller get back when the model is down, and why is that a marked error rather than an empty dict?

  5. Mission state and the main loop

    MissionSession holds everything that changes during a run. run_mission is the loop that advances it.

    You should be able to answerWhich two coroutines share the session, and which field keeps them from writing the plan at the same moment?

  6. Perception and plan changes

    Each camera frame passes three gates before it can change anything. The last gate is plain Python on purpose.

    You should be able to answerWhich verdict makes the rover ask a person, and which one is applied without asking?

  7. The rover interface

    One abstract class, three implementations. The mission code uses hasattr checks to find out which extras (hop, pivot, get_frame) a rover has.

    You should be able to answerWhat does run_mission do for a rover that has no get_frame?

  8. The approach controller

    The longest function in the project. Read it with the Approach controller flow open next to it, and read the small helpers first.

    You should be able to answerList the reasons it can return "blocked". Which one is caused by the sonar?

  9. Conditions and looking around

    The newest additions. The planner only offers "check" when the command has an if, and run_mission handles the yes/no branch itself, before the rover is asked to do anything.

    You should be able to answerWhich steps run when the check answers "no", and what happens when the model says "unsure"?

  10. Recovery and the report

    A blocked step does not end the mission straight away. It asks a person what to do, up to a limit, and then the run is written to disk.

    You should be able to answerIn how many different ways can the guidance loop end the mission?

  11. Room scan and the virtual room

    Two side topics that feed the main flow: where the room digest comes from, and the typed room the virtual rover drives on.

    You should be able to answerWhat is the difference between SCENE_SOURCE=video and SCENE_SOURCE=room for the VLM?

        Loose ends found while mapping

        Things the call graph or a grep turned up. None of them stops the system working; they are worth knowing before someone asks.

        NAV_MODE has two different defaults

        When NAV_MODE is unset, planner.py:37 and planner.py:212 assume "free" while mission.py:1623 and planner.py:115 assume "line". Your .env sets NAV_MODE=free, so today they agree. The comment beside it in .env still says "not read anywhere yet".

        Conditional and scan steps only work on the Pi rover

        planner_virtual has no "check" action, so a virtual run never plans one. _run_check and _scan_look both need get_frame (and _scan_look needs set_gimbal), which only PiRoverController has. On any other rover a check step returns blocked.

        An unsure condition gets the generic guidance question

        A check that answers "unsure" returns blocked with reason condition_unsure. _guidance_question has no wording for that reason, so the rover speaks its default: "I stopped because I could not complete the step. What should I do next?"

        mission._arrived is never called

        The arrival test lives inline in approach_controller (the sonar_hit and vision_hit lines). This older helper is left over.

        nav.path_length is never called

        No caller in brain/ or tools/.

        audio_capture.py is imported by nothing

        It is the early local-microphone recorder. The Pi client keeps its own copy of the recording code and only mentions this file in comments.

        Phase.REPORTING is declared and never set

        The dialogue phase enum has a REPORTING value, but no code assigns it. After execute the session stays EXECUTING.

        /ws/audio has no caller

        Neither the dashboard nor the Pi client opens it. /command is still used by the dashboard's one-shot panel, and both end in pipeline.handle_voice_command, the original single-shot flow.

        main.py imports from pipeline three times

        Lines 13, 24 and 34 import overlapping names. Harmless, and a quick tidy-up.
