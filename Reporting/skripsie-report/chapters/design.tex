\mysection{User and functional requirements}{User and Functional Requirements}
\label{sec:requirements}
The end user in mind is someone who is not staring at a screen. It is someone who would be able
tel a indoor rover what to do using speech. They are also not necessarily going to watch a screen 
to see if the rover is on track. They can say things like 'Go look at the box on the room' or 
'what is on the floor under the bed'. The rover will have to clarify if there is multiple boxes
or where the bed is in the room. Ask any questions to resolve ambiguity and then go and execute it's 
plan.

In the table below is the requirements in Table~\ref{tab:requirements}. Each one traces back to an objective in
Sections~\ref{sec:objectives}.

\mysection{System architecture}{System Architecture}

\mysubsection{Off-board inference and the thin-client split}{Off-board Inference}
\label{ssec:split}
The rover used is a HiWonder TurboPi with a Raspberry Pi 5 and about 4GB of RAM. The Turbo Pi has 
and expansion module called the HiWonder Echo pro microphone and audio adapter connected via USB 
The planner, whisper translator module and Vision model runs on a separate host machine. Keeping only the
motion and sensing on the Pi itself. The reason for this configuration is due to size. The 3 models together take about
~10GB of RAM and if that is excluding the stack required to drive the PI and control the camera. There is physically enough room
to have a reasoning model on this hardware. Not yet atleast.

Running the models on a seperate machine with more hardware capability also means that I can swap a model
by changing one environment variable, which the cloud comparison depends on.

I call the seperate machine hosting the models 'the brain'. It communicates to the turboPi over a rosbridge on a port
that it exposes. Using a library called 'roslibpy' (Figure~\ref{fig:split}). This allows for commands from the brain like: The plan,
the keyframes, vision results, and questions for the user to be sent to the rover. The Camera frames, sonar readings And
step results come back to the brain. 

since the brain hosts all the model decisions and state of the current plan. If there is a network drop the rover can still continue operating
with the last known plan. It just cannot ask for clarification or get new plans.

The code boundary is one method, \texttt{RoverController.execute\_step}. The brain
hands it one step and gets back \texttt{ok}, \texttt{blocked} or \texttt{halted}.
Everything above that method is the same for the real rover and for a simulated
one, so I can run the same dialogue and mission code in simulated room which is a constructed 
room from a JSON file before
putting it on hardware.

The default configuration is fully local. Speech recognition is
\texttt{faster-whisper} with the \texttt{fluister-turbo} model, the planner is
\texttt{gemma4:e4b} \texttt{gemma4:e4b}, and the vision model is \texttt{qwen2.5vl:3b} or \texttt{gemma4:e4b}. Both are
served by Ollama with a context of 8192 tokens. 


Speech output uses Piper, a small neural text-to-speech engine that runs locally.
It turns text into a waveform with a voice model stored as an ONNX file, and I use
the \texttt{en\_US-lessac-medium} voice. I chose it for three reasons. The rest of
the pipeline is local, so the rover's voice has to be local too (NR1), and a cloud
speech service would put a network call and a third party into every spoken
reply. Piper also runs on the CPU so it does not compete with the Vision and planner models
for VRAM. One thing to note if I use 1 model for both vision and reasoning, I would have 
more VRAM at my disposal.

The 8192-token window is a constraint I check instead of assuming. Every
clarification turn and every recovery turn adds text
to a prompt. The small local model usually silently truncate plans without
raising any error. A separate offline tool, \texttt{context\_budget.py}, counts
the tokens each part of the prompt takes (fixed instructions, room digest, one
clarification turn, one recovery turn) so that I know how many turns fit before the
window is the limiting factor. 

\mysubsection{Two-rate control: waypoint intents versus the reactive layer}{Two-rate Control}
\label{ssec:rates}

Everystep or run requires the rover to do a vision-model call. In order to process, where
it is at the current time and if it is still on track. A vision-model call takes about 4.78\,s
on my hardware. If the rover is using the line follower to control the driving, The steering of the rover
cannot occur in a closed loop. 

Instead there is a reactive layer on the turboPi itself, that came stock with it. It reads the sonar at 10-30\,Hz
and stop the rover if something is in the way. It also follows a line from the IR array uder the rover without consulting 
the models. The actual decision making engine runs on the brain at a pace  of the models and hardware. It chooses the next steps,
deciddes whether the rover has arrived at the desired destination. Where the closed loop system occurs is at 
every step boundary and at distinctive times during the rovers runs. 

The reason it is design like this is because the rover never relies on the vision model to make a immediate decision on when to stop
If a obstacle arises infront of the rover.


\mysubsection{The end-to-end pipeline}{Pipeline}
\label{ssec:pipeline}

The Figure~\ref{fig:pipeline} gives you a the overview of the process of one command, given to the rover. A short walkthrough video is recorded
of the room the rover will be traversing ing. The then breaks up the video of the room into keyframes (the number depends on the environment variable set). The vision
model them lists all the objects it sees in the in each frame as well as any obstructions in the image.  This is called the scene digest which can be called on by the model to
understand the environment. It is capped at 8 major objects with each having 2 attributes for each object. The reason it was capped at 8 objects so that it fits the planners prompt
without the dialogue. 

I chose text over a map delibreatly. A map is a seperate system to create and keep updating and generating one is outside the scope of my Skripsie.

A spoken command by someone is then transcribed and enters the clarification loop (Section~\ref{sec:clarification_design}).
If the command is not flagged as ambiguous the planner can turn is into steps using the actions and vocabulary/actions the rover can execute.
(Section~\ref{sec:vocabulary}). The vision model then checks the plan against the digest for steps that are not able to be executed. If it comes back successful the
plan is read back to the command giver and the rover only moves after they confirm the plan. The rover then run the steps one at a time and at the end reports are logged and spoken.

A Websocket will be used to carry the dialog sessions. \texttt{/ws/dialogue} will serve everything up until the confirmation, and \texttt{/ws/execution}
servers all the communication during the mission run. I keep them apart so that the dialogue state and the mission state never share a single session.

\mysection{The capability vocabulary}{The Capability Vocabulary}
\label{sec:vocabulary}

Since these planners are LLMs and have generalized knowledge, a planner based on a LLM may write any step it likes and will also write steps that the rover 
cannot execute. Commands like 'bring me that bottle' invites a \texttt{pick\_up} step. Since our rover has not arm. I gave the planner a fixed list of actions and 
in the prompt describe which exists and what each of these actions means. 

The list depends on the rover, so it lives in a planner profile. If a different hiWonder Rover is chosen, the 
actions can be overridden using a different configurtion of Planner.
The Real rover has the following actions: \texttt{follow\_line}, \texttt{move},
\texttt{turn}, \texttt{approach}, \texttt{scan}, \texttt{observe}, \texttt{stop}
and \texttt{report}. Every step that the rover executes is a small JSON object with an id, an action and a target.

The simulated rover has the same actions except for \texttt{follow\_line}. The \texttt{move} and \texttt{turn} step both 
carry a distance and an angle. The reason for that is the simple fact that the simulated rover can measure distance travel 
since the virtual room in which it travels has a define width and length. The real rover does not have this information about the 
room in which it is traveling. This was chosen in (NR3). The simulated rover also cannot pick up things as it has no arm and cannot
carry anything. These are all decided in the planner profile for the simulated rover. 

There is a ninth action that is \texttt{check}, this allows the rover to 'look at the destination object and decide whether
the condition is met' (Section~\ref{sec:conditional}). This action only takes place when the command contains a words like: 
\emph{if},\emph{whether}, \emph{otherwise} or \emph{unless}. The prompt then gets a extra block that explains the \texttt{check} step
as well as the optional \texttt{when} option for the alternative. This gives the rover 2 options to choose from before executing the plan.
The checked field is left out of everyother prompt for two reasons. The first reason is the extra line is more tokens take up in the already small
context window of 8192-tokens. The second is if there is extra context that the rover does not need it can results in a plan being miss interpreted or
inventing a condition that nobody spoke of. There is a limiting factor of deciding to use the \texttt{check} action with a word match is
that conditional phrased in a different way e.g 'when you see the door stop', will not be translated as conditional by the planner. Conditional logic also
only exists on the real rover's profile and not the simulated rover. 

The first plan generated by the planner that has actions outside of the list is not rejected. There are three methods used to catch it afterwards.
A step with an unknown action returns \texttt{blocked} status if the rover tries to run it. The reporting phase in the brain counts the out-of-vocabulary
actions in each plan the rover executes in orer to measure how often the planner ignors the list (section~\ref{sec:executability}). Before the rover goes off
on its mission the person hears the entire plan. I chose to measure the first-plan failure instead of just reprompting it and fixing the plan. 
The only plan action that is edited on the fly is the \texttt{move} action when the rover is in free mode. It changes the action to \texttt{approach}, since these two
actions are similar and the planner will try to use move instead of approach. 

The plan generated by the planner when the rover halts and ask for further instructions. This plan is used in the mission as is and not read-back to the user. This means that every step is validated 
to make sure the action is in the profile of the rover. Any plan that fails this check is discarded (Section~\ref{sec:recovery}). In free-roam mode the list for
a replan leaves out the \texttt{follow\_line}, since there is no floor line for it to follow.



\mysection{Clarification loop design}{Clarification Loop Design}
\label{sec:clarification_design}

\mysubsubsection{Where the loop sits}{Placement}

Some spoken commands are often underspecified, and if the rover executes on the wrong assumption it could place it in the wrong place.
The ambiguity is handeled at 3 distinct places. 

Before the departure, the system asks for a clarifying question if the command is unclear or ambiguous. During the mission it does not stop
to ask about any ambiguity. It compares what is currently can see with the digest and corrects itself as best as it can (Section~\ref{ssec:revision}).
When it reaches its destination it communicates what is still was unsure about. Any mid-mission ambiguity questions are left out on purpose since the command
speaker might not be there to answer the question but there is an exception for if the rover halted and cannot continue.

A rover that tries its best to execute a plan and get to a distinace is far better than one which stops and waits for a reprompt on a ambiguity it spotted in it's
current plan. This is different to what was seen in KnowNo~\cite{ren2023knowno} and Introspective Planning~\cite{liang2024introspective}, which ask for help
when their confidence drops.

\mysubsection{The dialogue as a state machine}{State Machine}
\label{ssec:statemachine}

The command spoke moves through multiple phases in Figure~\ref{fig:states}. 
During the \textt{CLARIFYING}, the vision model is used to determine whether the command is ambiguous. Using the given command and the scene digest. 
The vision models answer is in JSON with four fields: wether the command is ambiguous, why ,a question to ask, and  a rewritten command. If it is ambiguous, the quesiton is
spoken and the answer is added to the history. If it is clear, the rewritten command is sued from then on. The command only names objects and avoids words like 'left' or 'behind you'. 
Since those are relative to the camera view at the time of asking and can be completely wrong once the rover moves.

This clarifying loop is capped at five questions. If the command is still unclear after that, 
the system marks the session as capped and plans from the rewritten command if the model produced one 
after a question was answered or from the original command if no clarifying question was answered. 
The loop also drops a quetion it has already asked. If that is the only question that the model produces then there 
is nothing new to ask and the loop breaks and treats this as a cap moving onto the planning. A warning is added to the 
output plan when it is read-back to the user which starts with 'I am no fully sure I understoon', so the person
knows the plan is not 100\% certain. There is a cap to the number of questions asked since the user can get tired of answering
questions or it can result in a endless ambiguous loop of questions and answers. 

If the vision model ever fails to load. It is retired once and if it fails again, the person is told and asked to repeat their
command again. Not having this fall back coould result in letting every command through.

\mysubsection{Checking the plan before reading it back}{Plan Check}
\label{ssec:plancheck}

After the planner model produces a plan. The vision model can then check it against the digest
and returns whether it is workable and a list of concerns. If it says no, the planner
runs once more with the concerns added as advice while the original goal stays as it was. 
The replan happens only once. Replanning a second time rarely fixes what the first replan missed. If the plan checker
itself is unavailable, the answer is neither yes nor no, and skipping the plan check is safer than the model hallucinating a concern.

\mysubsubsection{Confirmation}{Confirmation}
\label{ssec:confirmation}

The plan is read back as a short sentence per step. The rover then awaits for confirmation from the user and does not
execute any steps until the confirmation is given. The answer provided is classified in two stages. All the keywords 
are passed over English phase list for all the possible combinations of 'no' and 'yes'. First the reject list is checked 
before the confirm list,`so 'no, dont't go` is not read as 'yes' because it contains 'go'. If nothing is classified as either 'yes' or 'no'. The 
rover counts that as unclear and the rover asks for the plan confirmation again. 

If the plan is rejected the system asks what it should change and returns to \texttt{CLARIFYING} with the answer in
the history, so that only one step coul be amended without starting over.

All commands can only be executed vocally however for debug purposes there is a typed input available. It can only be turned on if the 
environment variables is set for \texttt{ALLOW\_TEXT\_COMMANDS}. 

\mysubsection{The two later moments}{Later Moments}
\label{ssec:revision}

As the rover is moving, the second moment is self-correction. As a step is executed, new frames are compared with the digest.
A small module, \texttt{revision}, classifies what it sees into the following categories: no change, reroute, a material change or a 
block. This revision is done without a vision model but normal python code. The planner can be consulted to make a change,
but the classifier decided whether the person has to be asked. When the next step is exectued a reroute is applied. A material change moves the mission into
\texttt{AWAITING\_REVISION\_CONFIRMATION}, and the rover waits for a spoken yes
before it follows the new plan. The third moment is the report
(Section~\ref{sec:report}).

\mysubsection{The line follower as the reactive layer}{The Line Follower}
\label{ssec:line_follower}

Section~\ref{ssec:rates} showed that the Mac-hosted models cannot sit in a
steering loop. A VLM call takes about 15\,s, and keeping a mecanum chassis on a
line needs control at 10 to 30\,Hz. I therefore left steering to the TurboPi's
stock \texttt{line\_follow} ROS2 node, which closes the loop on the Pi using the
chassis-mounted 4-channel IR array. I used the IR array instead of the gimbal
camera so the camera stays free for the VLM to look wherever the mission needs,
regardless of where the chassis is steering (\texttt{rover\_pi.py},
\texttt{aim()}).

\texttt{PiRoverController} does not reimplement steering. It only supervises the
node on three things the node has no logic for itself:
\begin{itemize}
  \item Arrival: the node's own \texttt{/line\_follow/crossroads\_stop} topic
    decides when the end of the line is reached, not a model's judgement.
  \item Obstacles: the ultrasonic sensor is polled independently of the line
    sensor. Two consecutive readings below the stop threshold pause the follower
    until the path clears, and then it resumes.
  \item Giving up: a wall-clock timeout. The stock node has no lost-line exit,
    so without one the rover would drive straight on indefinitely.
\end{itemize}

I also use a modified variant, \texttt{line\_follow\_corner.py}. When it takes a
90\textdegree{} bend instead of parking at a crossbar, it publishes a
\texttt{/line\_follow/corner} event. This lets a route be given as an ordered
string of turns (e.g.\ \texttt{"L"}, \texttt{"R"}) and not only the
straight-track default. It adds one constraint: a planned pause, such as a
mid-drive look, must not land while the follower is mid-pivot. A \texttt{STOP}
sent during the node's pre-turn nudge cancels the turn instead of the forward
motion. \texttt{corner\_guard\_active()} reports a short window after each bend,
and callers must defer their pause until it ends.

Halting the follower is where a naive design fails without any error. While
running, the node republishes \texttt{/cmd\_vel} at 100\,Hz, so a single
zero-velocity \texttt{Twist} is overwritten within 10\,ms and the rover keeps
driving. \texttt{halt()} therefore sends an explicit \texttt{STOP} service call
to the node \emph{before} the zero \texttt{Twist}. It repeats both 0.7\,s later,
in case the first \texttt{STOP} landed inside the node's pre-turn nudge window
and was swallowed. This is the most safety-critical part of the hardware
integration.
