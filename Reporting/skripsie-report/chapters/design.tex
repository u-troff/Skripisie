\mysection{User and functional requirements}{User and Functional Requirements}
\label{sec:requirements}
The end user in mind is someone who is not staring at a screen. It is someone who would be able
tel a indoor rover what to do using speech. They are also not necessarily going to watch a screen 
to see if the rover is on track. They can say things like 'Go look at the box on the room' or 
'what is on the floor under the bed'. The rover will have to clarify if there is multiple boxes
or where the bed is in the room. Ask any questions to resolve ambiguity and then go and execute it's 
plan.

In the table below is the requirements in Table~\ref{tab:requirements}. Each one traces back to an objective in
Sections~\ref{sec:objectives}.

The rover travels and moves in open-loop steps but gets corrected once a step is completed or 
a obstacle is encountered by camera and ultrasonic sensors.

\mysubsection{Off-board inference and the thin-client split}{Off-board Inference}
\label{ssec:split}
The rover used is a HiWonder TurboPi with a Raspberry Pi 5 and about 4GB of RAM. The Turbo Pi has 
and expansion module called the HiWonder Echo pro microphone and audio adapter connected via USB 
The planner, whisper translator module and Vision model runs on a separate host machine. Keeping only the
motion and sensing on the Pi itself. The reason for this configuration is due to size. The 3 models together take about
~10GB of RAM and if that is excluding the stack required to drive the PI and control the camera. There is physically enough room
to have a reasoning model on this hardware. Not yet atleast.

Running the models on a seperate machine with more hardware capability also means that I can swap a model
by changing one environment variable, which the cloud comparison depends on.

I call the seperate machine hosting the models 'the brain'. It communicates to the turboPi over a rosbridge on a port
that it exposes. Using a library called 'roslibpy' (Figure~\ref{fig:split}). This allows for commands from the brain like: The plan,
the keyframes, vision results, and questions for the user to be sent to the rover. The Camera frames, sonar readings And
step results come back to the brain. 

since the brain hosts all the model decisions and state of the current plan. If there is a network drop the rover can still continue operating
with the last known plan. It just cannot ask for clarification or get new plans.

The code boundary is one method, \texttt{RoverController.execute\_step}. The brain
hands it one step and gets back \texttt{ok}, \texttt{blocked} or \texttt{halted}.
Everything above that method is the same for the real rover and for a simulated
one, so I can run the same dialogue and mission code in simulated room which is a constructed 
room from a JSON file before
putting it on hardware.

The default configuration is fully local. Speech recognition is
\texttt{faster-whisper} with the \texttt{fluister-turbo} model, the planner is
\texttt{gemma4:e4b} \texttt{gemma4:e4b}, and the vision model is \texttt{qwen2.5vl:3b} or \texttt{gemma4:e4b}. Both are
served by Ollama with a context of 8192 tokens. Speech output uses Piper with the
\texttt{en\_US-lessac-medium} voice. Cloud providers go through the same
interface, and I use them only as a comparison to the local models

The 8192-token window is a constraint I check instead of assuming. Every
clarification turn and every recovery turn adds text
to a prompt. The small local model usually silently truncate plans without
raising any error. A separate offline tool, \texttt{context\_budget.py}, counts
the tokens each part of the prompt takes (fixed instructions, room digest, one
clarification turn, one recovery turn) so that I know how many turns fit before the
window is the limiting factor.

\mysubsection{The line follower as the reactive layer}{The Line Follower}
\label{ssec:line_follower}

Section~\ref{ssec:rates} showed that the Mac-hosted models cannot sit in a
steering loop. A VLM call takes about 15\,s, and keeping a mecanum chassis on a
line needs control at 10 to 30\,Hz. I therefore left steering to the TurboPi's
stock \texttt{line\_follow} ROS2 node, which closes the loop on the Pi using the
chassis-mounted 4-channel IR array. I used the IR array instead of the gimbal
camera so the camera stays free for the VLM to look wherever the mission needs,
regardless of where the chassis is steering (\texttt{rover\_pi.py},
\texttt{aim()}).

\texttt{PiRoverController} does not reimplement steering. It only supervises the
node on three things the node has no logic for itself:
\begin{itemize}
  \item Arrival: the node's own \texttt{/line\_follow/crossroads\_stop} topic
    decides when the end of the line is reached, not a model's judgement.
  \item Obstacles: the ultrasonic sensor is polled independently of the line
    sensor. Two consecutive readings below the stop threshold pause the follower
    until the path clears, and then it resumes.
  \item Giving up: a wall-clock timeout. The stock node has no lost-line exit,
    so without one the rover would drive straight on indefinitely.
\end{itemize}

I also use a modified variant, \texttt{line\_follow\_corner.py}. When it takes a
90\textdegree{} bend instead of parking at a crossbar, it publishes a
\texttt{/line\_follow/corner} event. This lets a route be given as an ordered
string of turns (e.g.\ \texttt{"L"}, \texttt{"R"}) and not only the
straight-track default. It adds one constraint: a planned pause, such as a
mid-drive look, must not land while the follower is mid-pivot. A \texttt{STOP}
sent during the node's pre-turn nudge cancels the turn instead of the forward
motion. \texttt{corner\_guard\_active()} reports a short window after each bend,
and callers must defer their pause until it ends.

Halting the follower is where a naive design fails without any error. While
running, the node republishes \texttt{/cmd\_vel} at 100\,Hz, so a single
zero-velocity \texttt{Twist} is overwritten within 10\,ms and the rover keeps
driving. \texttt{halt()} therefore sends an explicit \texttt{STOP} service call
to the node \emph{before} the zero \texttt{Twist}. It repeats both 0.7\,s later,
in case the first \texttt{STOP} landed inside the node's pre-turn nudge window
and was swallowed. This is the most safety-critical part of the hardware
integration.
